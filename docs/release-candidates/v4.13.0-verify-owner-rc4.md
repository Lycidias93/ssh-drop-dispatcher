## Shared WebUI foundation

RC4 consumes the common standalone foundation from:

- repository: `Lycidias93/android-root-module-webui-template`
- pinned commit: `5b8e412428cd04b1cf98a1fc0e03269580b60d71`
- core version: `0.2.2`
- lock file: `webui-core.lock`

The builder verifies exact Git blob identities for the imported frontend and server source before compiling the ARM64 Android server.

Security/architecture contract:

- Action button starts a short-lived native server on `127.0.0.1` using a dynamic port.
- Bootstrap token is passed through a private `0600` file, consumed once and replaced by an HttpOnly session cookie.
- Browser ends on a clean token-free URL.
- exact loopback/Host/origin protections remain owned by the shared core.
- no CDN, cloud or companion-app dependency.
- WebUI is not a boot dependency.
- JavaScript does not build arbitrary shell commands.
- browser input cannot choose arbitrary runtime paths or arbitrary commands.
- all mutations are named typed adapter operations validated again in `module-control`.

## RC4 information architecture

### Overview

Compact operational summary rather than raw `service.sh` text:

- health
- queue/inflight
- failure count
- quarantine count
- target count
- last delivery state / receipt context
- notification state
- positive safety assertions

The target overview follows the compact visual direction of the existing four-target view: `berylax`, `pi3`, `pi4`, `zeropi2` stay immediately recognizable. Detailed Target Matrix data is typed and secret-safe rather than a raw config dump.

### Target Matrix

Read-only typed inventory:

- target name
- enabled state
- explicit shell profile
- SCP profile (`-O` visible for BerylAX where applicable)

Explicitly excluded:

- SSH host/address
- remote drop path
- key paths/content
- network addresses

Target readiness/verification is exposed through separately declared bounded jobs (`Test pi3`, `Test pi4`, `Test ZeroPi2`, `Test BerylAX`) so the UI does not execute arbitrary target names.

### Workflow inventories

Read-only views:

- Queue: RC3 delivery ID, file, state, target names
- Quarantine: recent file/target/reason records
- Failures: bounded redacted failure evidence
- Delivery receipts: recent RC3 delivery ID/file/final state/scan scope

These use RC3 workflow data rather than reconstructing state in JavaScript.

### Diagnostics

Bounded background jobs:

- combined `doctor --chatgpt` + `incident --chatgpt`
- fixed target tests
- existing secret-safe `issue.txt` generation

Logs remain bounded through the typed core endpoint.

### Control

Declared actions:

- Enable dispatcher: safe, dry-run supported
- Disable dispatcher: caution, dry-run + exact `DISABLE` confirmation
- Run queue scan: danger, dry-run + exact `DISPATCH` confirmation
- Send ntfy test: safe
- Clear ntfy secrets: danger, dry-run + exact `CLEAR NTFY` confirmation

The queue-scan action is explicitly **not** target-only delivery. It is blocked by the adapter when `scan.lock`/`scan.lock.ts` is present to avoid amplifying the known follow-up-scan contention issue.

RC4 deliberately does not expose a free-text requeue/path action. Recovery remains a CLI/controlled-workflow operation until a typed selection/identity contract is proven.

## Ntfy settings

WebUI configuration is secret-safe:

- enabled, priority and tags can be read and changed;
- topic, URL and token-file path are write-only fields in the browser;
- blank secret fields preserve the existing value;
- status reveals only configured/not-configured state;
- explicit `Clear ntfy secrets` is required to remove secret references.

No topic/token content is returned through status/config APIs.

## Public-promotion checklist

Installed-runtime acceptance is not the same as public release promotion. Before promoting `update.json` or creating a public release/tag, retain the broader release checks as applicable:

1. exact RC4 ZIP identity and inline SHA-256;
2. controlled Magisk install/reboot proof;
3. exact module/runtime version `4.13.0-verify-owner-rc4` / `4130004`;
4. existing RC3 service/CLI/workflow invariants still PASS;
5. Action/browser behavior remains loopback-only and token-safe;
6. bootstrap token/session behavior remains secret-safe;
7. typed status and inventories expose no host/drop/network/secret fields;
8. Target Matrix shows configured targets without private host/drop data;
9. diagnostics jobs remain bounded;
10. dry-run/confirmation gates remain correct for control actions;
11. dispatch scan remains blocked under active scan lock;
12. ntfy write-only/preserve behavior remains verified without logging secrets;
13. WebUI closure/failure must not affect Dispatcher service health;
14. perform a separately bound remote target-delivery smoke before claiming a new RC4 target-delivery capability;
15. public release/update-channel changes require an explicit promotion action.

The installed-runtime controller does not invent separate remote target-delivery evidence; that capability remains independently gated.
