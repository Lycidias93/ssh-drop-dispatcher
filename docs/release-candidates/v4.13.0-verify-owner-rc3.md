# v4.13.0-verify-owner-rc3

Status: source candidate; Pixel installed runtime remains verified RC2 until RC3 post-boot runtime verification succeeds.

RC3 keeps the verified RC1/RC2 delivery and verification engine and adds a workflow/observability layer designed to reduce ChatGPT/Termux round-trips without weakening delivery safety.

```text
version=4.13.0-verify-owner-rc3
```

## RC3 focus

- Derived delivery correlation ID based on the existing dispatcher record identity.
- Per-delivery trace and inspection without rewriting historical state.
- Queue, recent failure and quarantine inspection.
- Read-only/no-upload delivery preflight.
- Safe `dispatch-file <file> --wait` orchestration using the existing dispatcher scan and wait logic.
- Versioned JSONL delivery receipts.
- Compact redacted incident context for ChatGPT/Codex.

## Delivery identity

RC3 does not add a competing transport identity. It derives:

```text
SDD-<cksum-crc>-<bytes>
```

from the existing dispatcher record:

```text
<basename>|<cksum-crc>:<bytes>
```

This allows tracing existing done/complete/inflight/quarantine records while leaving the transport state model unchanged.

## Preflight contract

`SDD_PREFLIGHT_V1` performs no upload. It checks local file validity, config lint, filename routing, dispatcher enabled state, explicit per-target shell syntax, SSH/readiness, remote drop writability and the existing free-space policy.

The remote readiness phase is read-only and therefore may report `host_run=yes`; SCP and the normal dispatcher scan path are not invoked by preflight.

## Dispatch workflow contract

`dispatch-file --wait` deliberately does not duplicate `process_file()`.

Its sequence is:

```text
preflight -> existing dispatcher scan -> wait-delivery -> receipt
```

The normal scan can process other already-ready dispatcher artifacts in the scan directory. The resulting receipt therefore makes the scope explicit:

```text
scan_scope=existing_queue
automatic_requeue=no
remote_sha_required=yes
```

There is no automatic retry or requeue after a failure or timeout.

## Delivery receipt

Schema:

```text
SDD_DELIVERY_RECEIPT_V1
```

Receipts are appended to:

```text
/data/adb/ssh-drop-dispatcher/delivery.receipts.jsonl
```

They are workflow evidence only. `dispatch.done`, `dispatch.complete`, quarantine state and the existing remote SHA verification remain delivery truth.

## Incident context

Schema:

```text
SDD_INCIDENT_CONTEXT_V1
```

The incident surface contains health/lint state, optional delivery state/reason, state counts, recent WARN/FAIL counts and a safe next action. It explicitly redacts host fields, remote drop paths, network addresses and secret content.

## Safety boundaries

RC3 does not change:

- filename routing contract;
- target drop directories;
- dispatcher-owned remote syntax verification;
- normal-path remote SHA-256 parity;
- fail-closed Bash behavior;
- BerylAX `sh` and `scp -O` behavior;
- host payload non-execution policy;
- Python delivery policy;
- DNS, HA, VIP, default/static routes, MagicDNS or subnet routes.

RC3 adds no network self-healing, automatic quarantine deletion, automatic retry/requeue or payload execution.
